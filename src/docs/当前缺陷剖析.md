# 当前缺陷剖析

> **文档性质**：基于源码审查的问题清单，非运行时故障报告。
> **审查范围**：`BiSheng.Latte`（WPF 客户端）、`BiSheng.Server`（同步服务端）、`BiSheng.Shared`（同步契约）。
> **审查日期**：2026-07-20
> **总体结论**：核心同步与数据安全逻辑设计严谨、测试充分，未发现正确性缺陷。本文记录的是**可扩展性隐患、资源累积、工程完备性缺口**，以及若干需明确说明的**架构权衡**（非缺陷）。

## 严重度分级

| 级别 | 含义 |
|------|------|
| 中 | 在特定规模/场景下会显著影响性能或体验，建议排期处理 |
| 低 | 长期缓慢累积或工程完备性缺口，不影响日常使用，可在迭代中补齐 |

## 一、确认的缺陷与隐患

### 1.1 【中】全量快照 Pull 存在 N+1 查询与全量 Id 内存加载

- **位置**：`BiSheng.Server/Services/SyncService.cs` → `PullEntitySnapshotAsync`
- **现象**：当客户端 `since <= 0`（首次同步或全量重建）时，服务端先执行
  `db.Folders.Where(...).OrderBy(f => f.Id).Select(f => f.Id).ToListAsync()` 把该用户**全部**文件夹 Id 载入内存，笔记 Id 同理；随后在 `foreach` 中对每个 Id 逐条 `FirstOrDefaultAsync` 查询实体再构建 DTO。
- **原因**：采用了"先取 Id 列表、再逐个查实体"的直观实现，未使用批量 `WHERE Id IN (...)` 或键集分页（keyset pagination）。常规增量路径（`PullIncrementalAsync`）按 SyncLog 分页，不受此影响；问题仅存在于快照重建路径。
- **影响**：
  - 大型笔记库（数万条）下产生典型 N+1 查询，快照重建耗时随实体数线性放大；
  - 全部 Id 一次性 `ToListAsync` 载入内存，带来不必要的内存峰值；
  - 触发时机为首次同步 / `RequiresFullSync` 全量重建，属低频但高代价操作。
- **改进方向**：按 Id 区间分批 `WHERE Id IN (...)` 批量取实体，或改为键集分页（`WHERE Id > lastId ORDER BY Id TAKE pageSize`），逐批构建 DTO，避免一次性载入全部 Id。

### 1.2 【中】SyncLog.Payload 与实体正文冗余存储

- **位置**：`BiSheng.Server/Services/Mutations/EntityChangeWriter.cs`（写 `SyncLog.Payload`）+ `Data/Entities/SyncLog.cs`
- **现象**：笔记全文既持久化在 `Note.Content`，又在每次变更时**完整**写入 `SyncLog.Payload`（JSON 字符串）。文件夹同理（字段较少，影响小）。
- **原因**：增量同步需要把变更的完整内容随 SyncLog 下发给其他设备——终态折叠（`BuildFromEntityAsync`）与快照重建都依赖 Payload 还原实体终态。设计上选择了"日志即完整变更快照"，以简化下游读取与折叠逻辑。
- **影响**：
  - 大笔记 + 高频编辑的用户，SyncLog 表在裁剪前的峰值体积可观（同一笔记的多个历史版本各存一份全文）；
  - `SyncLogCompactor` 按版本裁剪（安全线 = `min(活跃设备 LastSyncVersion)`）能控制稳态体积，但**裁剪前的峰值**与单条大 Payload 的内存占用（Push 冲突检测时 `missedLogs.ToList()`，已有 `MaxMissedSyncLogsForPushConflict=2000` 上限保护）仍需关注。
- **改进方向**：评估 Payload 仅存变更字段（delta）或对超大正文做引用/压缩；权衡是终态折叠与快照重建逻辑会相应变复杂，需与同步协议契约（`BiSheng.Shared`）协同演进。

### 1.3 【低】已解决的冲突记录（SyncConflict）无清理，单调累积

- **位置**：`BiSheng.Latte/Data/Entities/SyncConflict.cs`、`Services/SyncService.cs`（`ResolveKeepLocal/KeepRemote/Merged`）、`Services/Sync/SyncRemoteChangeMerger.cs`
- **现象**：冲突解决仅将 `IsResolved` 置为 `true`（`db.SyncConflicts.Update`），**从不删除**记录；创建时仅对"同一实体的**未解决**冲突"去重（`SyncRemoteChangeMerger` 中 `db.SyncConflicts.Any(c => ... && !c.IsResolved)`）。每条 `SyncConflict` 同时保存 `LocalContent`、`RemoteContent`、`LocalPayload`、`RemotePayload` **四份正文副本**。
- **原因**：设计上把冲突表当作"待用户处理的工单"，解决后作为历史保留，未设计归档或清理策略。
- **影响**：长期使用的本地库中 `SyncConflicts` 表持续增长，且每条含多份正文副本，逐步占用磁盘；未解决冲突计数虽走索引不受影响，但表整体体积无界。
- **改进方向**：对 `IsResolved = true` 的冲突做定期清理或归档（如仅保留最近 N 条 / N 天），可在现有的本地库维护流程（journal 修剪、回收站清理同级）中追加一步。

### 1.4 【低】编辑器核心缺少自动化测试覆盖

- **位置**：`tests/Bisheng.Editor.Tests`
- **现象**：该工程是一个 WPF 应用（`App.xaml` / `MainWindow.xaml`），**未引用任何测试框架**，是用于交互式验证编辑器控件的手动宿主，而非自动化测试。与之对比，`BiSheng.Latte.Tests` 与 `BiSheng.Server.Tests` 均为 xUnit 工程且覆盖扎实。
- **原因**：编辑器控件（AvalonEdit 宿主、Markdown 渲染）依赖 WPF 交互，目前以手动宿主代替自动化验证。
- **影响**：README 强调的编辑器核心能力——"增量读取模型更新（避免大文档全量重建）"、纯文本提取（供搜索）等——缺少自动化回归保护，重构时易引入隐性回归。
- **改进方向**：将可单测的纯逻辑（增量更新算法、`NoteSearchTextExtractor` 类的文本提取、Markdown 解析）从 UI 宿主中剥离，补充 xUnit 测试；UI 相关部分可保留手动宿主。

### 1.5 【低】SECURITY.md 缺失

- **位置**：仓库根目录（README 的 *Project Layout* 中引用了 `SECURITY.md` 并标注 "to be added"）
- **现象**：经核实仓库中不存在 `SECURITY.md`。
- **原因**：文档尚未补齐。
- **影响**：作为开源自托管（且涉及笔记数据、API Key、TOTP）的项目，缺少安全漏洞上报渠道与响应流程说明，不符合开源安全最佳实践，也不利于外部研究者负责任地披露漏洞。
- **改进方向**：补充 `SECURITY.md`，说明漏洞上报方式（如私密邮箱/私有 issue）、受支持版本、响应时限。

## 二、架构权衡与已知限制（非缺陷）

以下事项是**有意的设计选择或技术栈固有特性**，记录在此以避免误判为缺陷，并在场景变化时作为演进参考。

### 2.1 服务端 SQLite 单写者并发上限

- **位置**：`BiSheng.Server`（EF Core + SQLite，`bisheng.db`）
- **说明**：多设备高频并发 Push 在 SQLite 单写者模型下会串行化。版本分配已用原生 `UPDATE ... RETURNING` 原子递增规避竞态（`UserSyncVersionService`），但底层仍是单写者。
- **为何不是缺陷**：项目定位为**个人自托管**（单用户、少量设备），SQLite 带来零配置、单文件、易备份（`sqlite3 .backup`）的运维优势，与定位匹配。
- **演进参考**：当前 EF Core 抽象良好，若未来支持小团队/多用户高并发，可评估迁移 PostgreSQL。

### 2.2 冲突采用"检测 + 通知"而非自动合并

- **位置**：`BiSheng.Server/Services/SyncService.cs`（`PushAsync` 返回 `OverwrittenChanges`）+ `BiSheng.Latte/Services/Sync/SyncRemoteChangeMerger.cs`
- **说明**：服务端对客户端变更采用 last-write-wins 应用，同时返回被覆盖实体的远端 pre-state（`OverwrittenChanges`），由客户端生成 `SyncConflict` 交用户手动选择"保留本地 / 保留远端 / 手动合并"。
- **为何不是缺陷**：笔记正文的自动三方合并复杂且易丢数据，刻意把决定权交给用户，配合数据安全策略（冲突双副本）属合理权衡。
- **关联隐患**：见 1.3——已解决冲突记录无清理。

### 2.3 国际化：当前仅简体中文

- **位置**：`BiSheng.Latte` UI 文案与代码注释
- **说明**：UI 文案与代码注释均为简体中文，尚无 `.resx` / 资源字典等多语言基础设施。
- **为何不是缺陷**：项目当前面向中文用户，英文 UI 已在 README 列为后续计划；中文注释是项目约定。
- **演进参考**：开源国际化推广前，需将 UI 文案外置为资源文件。

## 三、已核实为"非缺陷"的事项

为避免误导，以下曾被怀疑、但经源码核实**确认已妥善处理**的事项：

- **运行时数据不会误入版本库**：`.gitignore` 已正确排除 `*.db` / `*.db-shm` / `*.db-wal`（客户端 `local.db` 与服务端 `bisheng.db` 及其 WAL）、`**/uploads/`、`**/data-protection-keys/`、`.env` / `.env.*`。工作目录中存在这些文件属本地运行产物，不会被提交。
- **SyncLog 裁剪不会误删未同步数据**：安全裁剪线取 `min(活跃设备 LastSyncVersion)`，且 `GetServerVersionAsync` 刻意只刷新 `LastSeenAt` 不推进 `LastSyncVersion`，避免污染裁剪线导致丢改（见 `SyncLogCompactionService` 注释）。
- **API Key 与 TOTP 密钥不明文落库**：API Key 以 SHA256 哈希存储（`ApiKeyAuthHandler`）；TOTP 密钥用 Data Protection 加密（`TotpSecretProtector`），登录时自动将明文存量升级为密文。
